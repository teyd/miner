# Research 02 — The Twitch surface a miner touches (state on 2026-10-29)

_Researched 2026-10-29. Sources: DevilXD/TwitchDropsMiner (TDM, master @ 2026-10-28, issues),
rdavydov/Twitch-Channel-Points-Miner-v2 (TCPM, 2026-07-16), teyd/just-mining (2026-10-29),
help.twitch.tv. Twitch's private API is undocumented, so everything here is what working
clients currently do. "(inference)" / "(unverified)" are marked._

## TL;DR

- **This surface changes month to month.** In 2026 TDM changed its _watch method_ four times,
  its _login method_ once, and its GQL hashes or user agent about six times. Treat the Twitch
  contract as a separately versioned, probed and recorded layer.
- **Login:** since ~2026-09-18 the **device-code flow rejects the Android client ID**. The
  working path is the **implicit grant with the Android client ID**
  (`kd1unb4b3q4t58fwlpcbzcbnm76a8fp`), taking the token from the redirect fragment. TDM
  automates it with a browser (zendriver, 2026-10-25). just-mining has the user do it by hand
  with an authorize link and a console snippet. A headless miner can't log in on its own.
  **A revoked token means a human has to log in again.**
- **Discovery:** `ViewerDropsDashboard` / `DropCampaignDetails` returned **`null` without an
  error** for device-code tokens (TDM #1162/#1174) and fail the integrity check on the WEB client.
  They work with the implicit-grant Android token (TDM closed #1165 on 2026-10-25; just-mining
  uses them). **The silent `null` is the failure mode to design for.**
- **Credit limits:** drops progress on **one channel at a time** (Twitch help). Channel points
  accrue on **at most two streams at a time** (TCPM docs). When several campaigns share a stream,
  only one progresses at a time (TDM #756), and Twitch no longer says which drop is
  progressing (TDM #387).
- **Watching today:** fetch the lowest-quality HLS media playlist and `HEAD` its segments
  every ~20 s (TDM since 2026-10-09; just-mining the same). Spade `minute-watched` POSTs and the GQL
  `sendSpadeEvents` mutation both worked at some point in 2026.
- **Real-time:** `wss://pubsub-edge.twitch.tv/v1` still serves the client topics
  `user-drop-events.<id>`, `onsite-notifications.<id>` and `community-points-user-v1.<id>` (TDM and
  just-mining, Oct 2026).
- **Budgets are per IP, not per account:** ~**10 websockets per IP** and ~**5 GQL requests/s**
  (DevilXD, TDM #1153, 2026-08). Running "2 or 3 accounts shouldn't be too big of a deal, but anything more is
  considered abuse" from one IP (TDM #414, 2024). Every process on one host shares these limits.

## 1. Authentication

| Flow                                                            | Status (Oct 2026)                                                                       | Source                                                                |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Device code, `ANDROID_APP` client                               | **broken** since ~2026-09-18: `/oauth2/device` → `400 invalid client`                   | TDM #1165, PR text in #1174                                           |
| Device code, `SMARTBOX` (`ue6666qo983tsx6so1t0vnawi233wa`)      | gets a token, but campaign queries return `null`, so useless for discovery              | TDM #1165 (DevilXD 2026-09-21)                                        |
| Username/password `/login`                                      | gone. Replaced by `/protected_login` behind Kasada (the same anti-bot as integrity)     | TDM #1165 (2026-09-26)                                                |
| **Implicit grant, `ANDROID_APP` client, token in URL fragment** | **works**. TDM drives it via zendriver; just-mining via a manual link + snippet         | TDM commit c3be032 (2026-10-25), just-mining `docs/authentication.md` |
| `WEB` client token                                              | needs `Client-Integrity` for GQL; extracting it alone "does not yield a valid GQL call" | TDM #1165 (2026-10-08)                                                |

Consequences for a headless homelab miner:

- Token acquisition is a **human step**. Validate hourly (`GET /oauth2/validate`, Twitch's rule
  for apps holding a token). On `401`, stop and say so. Don't retry in a loop.
- Users must not "log out everywhere" or change their password, since that revokes the token
  (TDM #1165, 2026-10-08).

## 2. Discovery (what to mine)

- `Inventory` (in-progress campaigns, progress, `isClaimed`, `dropInstanceID`, account link
  state) works on every client token tried, including SMARTBOX/TV (TDM #1165 comment).
- `ViewerDropsDashboard` + `DropCampaignDetails` (all campaigns, with ACL/allowed channels)
  are the gated pair. Failure shape: `dropCampaigns: null` with **no GraphQL error**.
- `DropsHighlightService_AvailableDrops` per channel is the fallback people try. DevilXD says
  heavy use makes it "stop working for X days". It returns one campaign per channel, so a
  badge/emote campaign with no channel ACL can hide every other campaign (#1174, 2026-09-28).
- Game directory with the `DROPS_ENABLED` filter (`DirectoryPage_Game`) gives live candidates.

(inference) The miner needs a **"capability probe"** at startup and on every rescan that
asserts discovery returned a non-null catalog, and fails loudly with a named cause.

## 4. Watching (the actuator)

| Date (2026) | TDM watch method                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Apr 28      | add GQL `sendSpadeEvents` (gzip+base64 `minute-watched`)                                                                                                |
| Jul 11      | "Change the watching method back to using Spade" (POST base64 `minute-watched` to the `spade_url` scraped from the channel page)                        |
| Oct 9       | "Change the mining method to playlist HEAD requests": usher master → lowest-quality media playlist → `HEAD` each segment (~15 × 2 s chunks), every 20 s |

just-mining does the HLS approach too, with `PlaybackAccessToken`, usher, the media playlist and segment
`HEAD`s. It notes the client identity headers and the `Origin` header matter (commits
2026-10-28). `403`/`410` = the channel refuses playback (sub-only, geo); `404` = offline.

**Live check, 2026-10-30 15:31 (one read-only probe, teyd's account, Rust channel `oilrats`, 23
requests):** `PlaybackAccessToken` answers 200 with both hashes (`3093517e…`, `ed230aa1…`),
`authorization: { isForbidden: false, forbiddenReasonCode: "NONE" }`; the token's `value` is JSON
whose `expires` is **20 minutes** after issue. Usher (`usher.ttvnw.net/api/channel/hls/<login>.m3u8?sig&token`)
answers 200 with 4 variants (720p60 down to 160p30, lowest last); variant URLs are
`<cluster>.playlist.ttvnw.net/v1/playlist/<signed>.m3u8`, signed **in the path**, with no query. The
160p media playlist answered 200 twice 20 s apart, with 16 and 15 segments of 2 s at
`<id>.j.cloudfront.hls.ttvnw.net/v1/segment/<signed>.ts?dna=<signed>`; 12 segment `HEAD`s all
answered 200 (`application/octet-stream`, length 0 or absent). An offline channel's token still
issues, and usher then answers **404 `[{"error":"Can not find channel"}]`**. The master playlist's
`#EXT-X-TWITCH-INFO` carries `USER-IP` and opaque `C`/`E` values, and media playlists a signed
`X-TV-TWITCH-TRIGGER-URL`: all redacted now (`redact.ts`, `fixtures/leaks.json`). Headers sent:
the Android `User-Agent`, `Client-Id`, `X-Device-Id`, `Referer: https://www.twitch.tv/`, `Origin:
https://www.twitch.tv`, no `Authorization` to the CDN. Not checked: 403/410 shapes.

**Live run, 2026-10-30 15:19–15:56 (`miner run`, teyd's account, 37 min): HEADs alone credit.**
Every 20 s: the 160p media playlist plus a `HEAD` of each of its 15–16 segments, nothing
downloaded; 110 ticks, 3 playback tokens (refreshed before their 20 min expiry), no failures.
`drop-progress` frames rose about one minute per minute watched (3, 4, 6, 10, 11, 13, 15 of 15 on
one drop; Twitch skips some minutes' frames, never the count). Both earnable drops of the watched
campaign progressed at once (the second stood at 24 of 30 when the first completed), as the twin's
`dropsInCampaign` assumes. Two drops completed and were claimed about a second after the last
progress frame; **no `drop-claim` frame came**, the claim followed the progress and an inventory
read. A third claim, of a drop completed earlier, answered `isUserAccountConnected: false`.

**Claim.** `DropsPage_ClaimDropRewards` (TDM's `ClaimDrop`), hash `a455deea…`, variables
`{ input: { dropInstanceID } }`, identical in TDM `constants.py:328` (2026-10-28) and just-mining,
which sent it live 2026-10-28: a fresh claim and a re-claim of a claimed instance both answer
`status: "ELIGIBLE_FOR_ALL"`; an unlinked game account adds `isUserAccountConnected: false` (Twitch
grants it on linking); an unknown instance id answers `claimDropRewards: null`. TDM also treats
`DROP_INSTANCE_ALREADY_CLAIMED` as done (`inventory.py:207-213`), never seen in a recording. Not sent
by this repo outside a real `miner run`. Live 2026-10-30: 3 claims, one request each, all
`ELIGIBLE_FOR_ALL`.

(inference) Keep the watch method as a **pluggable strategy** behind one interface. History says
it will change again. The probe from §2 should also check "did inventory progress move within N
minutes of watching", because that is the only real signal that the actuator works.

## 4b. Accounts, IPs and linking

| Fact                                                                                                                                                | Source                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Twitch lets you enable extra accounts per verified email or phone                                                                                   | help.twitch.tv "Creating an Account with Twitch", "Managing Your Phone Number" |
| Suspending a phone-verified account also suspends accounts linked to that phone                                                                     | TechCrunch 2021-09-29 (unverified for 2026)                                    |
| Instances on one machine share Twitch's limits: ~10 websockets/IP, ~5 GQL req/s ("also per IP?")                                                    | TDM #1153 (DevilXD, 2026-08-29)                                                |
| 2–3 accounts from one IP is fine, more is "considered abuse". Twitch may detect one IP managing many accounts. No known account bans from the miner | TDM #414 (DevilXD, 2024-01)                                                    |
| TDM only mines campaigns the account is **linked** for, plus badge/emote campaigns if enabled (`Campaign.eligible`)                                 | TDM `inventory.py`                                                             |
| Twitch: "Link your game account FIRST" to earn in-game drops                                                                                        | help.twitch.tv "How Drops Work" (search snippet; the page is JS-rendered)      |
| Some games: you can _earn_ drops unlinked and link later to receive them. Entitlements get created for non-linked users                             | Funcom Conan Exiles FAQ; Twitch dev forums thread 62731 (2025-03)              |
| Badge/emote benefits are Twitch-side and need no game link (inference from TDM's eligibility rule)                                                  | TDM `inventory.py`                                                             |

Consequences (inference):

- **One host = one budget.** Parallel live runs on one machine compete for the same per-IP
  limits however many accounts they use. Either all accounts live in **one process with one
  shared rate limiter and socket pool**, or a host-wide broker hands out the budget.
- **Unlinked test accounts are still useful** for badge/emote campaigns, channel points, the watch
  actuator, inventory lag, switching and claims of Twitch-side rewards. Whether _game_ campaigns
  progress unlinked is campaign-dependent and is a lane-D question ([04](04-parallel-bug-finding.md)).
- Cap concurrent live accounts per IP at **2–3**.

## 5. Real-time and mutations

- PubSub edge as in the TL;DR: PING every 4 min with 10 s PONG timeout (just-mining). Twitch's
  former public PubSub docs asked for a PING at least every 5 min (background knowledge). Handle
  `RECONNECT` and back off.
  Twitch's own web client has moved to Hermes (`wss://hermes.twitch.tv/v1`, a PubSub-topic
  wrapper; TCPM #722 and PR #728, 2025), and public PubSub was shut down for third-party apps on
  2025-04-14 (Twitch dev forums). The edge still serves the Android token anyway.
- **Live check, 2026-10-30 (miner probe, teyd's account, one socket):** connect in 357 ms; PING →
  `{ "type": "PONG" }\r\n` (note the padding) in ~160 ms, twice; one LISTEN of 25 topics
  (`user-drop-events.<user>`, `video-playback-by-id.<ch>` and `broadcast-settings-update.<ch>` for
  12 live channels) → `RESPONSE` with `error: ""`. In 8 minutes: 191 `viewcount` frames (one per
  live channel about every 30 s), 3 `commercial`, no stream-up/down or settings change. A second run
  through `src/twitch/PubSub.ts` (2 min) did LISTEN, a diffed UNLISTEN + LISTEN and got 3 empty
  `RESPONSE`s. `drop-progress` shape: just-mining's log of 2026-10-29 (`current_progress_min` is the
  drop's total). `drop-claim` is from TDM `twitch.py` and not yet seen live by us. Fixtures:
  `src/twitch/fixtures/pubsub-frames.json`.
- **Live check, 2026-10-30 (`miner run --shadow`, 10 min, 100 channels + drops = 201 topics on 5
  sockets):** every socket got its own PONG to both PINGs, no reconnects. Seen live and matching
  TDM's shapes field for field: `stream-up` (`server_time` is an integer, `play_delay` 0),
  `stream-down`, and 17 `broadcast_settings_update` (13 title-only with `old_game_id == game_id`,
  4 category changes; `game_id` is a number). No `drop-progress` or `drop-claim` (nothing watched).
  If the edge goes away, Hermes is the fallback to build.
- Mutations seen in working clients: `ClaimDrop` (by `dropInstanceID`), `ClaimCommunityPoints`
  (bonus chest), `JoinRaid`, `MakePrediction`, `CommunityMomentCallout_Claim` (moments) (TCPM).
  (inference) A claim whose answer was lost may have succeeded, so a retry should read inventory
  first, never resend blindly.

## 6. Badges, emotes, and "reward campaigns"

- Inside **drop campaigns**, each benefit has a `distributionType`: `BADGE`, `EMOTE`,
  `DIRECT_ENTITLEMENT` (in-game items), else unknown (TDM `inventory.py`). TDM gates
  badge/emote campaigns behind a setting because ACL-less badge campaigns distort
  `AvailableDrops` (§2).
- **"Reward campaigns"** (shown on the drops page as "Open Reward Campaigns", e.g. quests) are a
  _different system_. DevilXD: "would essentially require creating a miner on its own" and will
  not support them (TDM #1162, 2026-09-28). (unverified) their GQL shape and completion rules.
  This needs a separate research spike before we commit to it.

## 7. Churn log (why the contract must be its own layer)

TDM commits touching Twitch constants in 2026: GQL hash updates on 05-16, 07-14, 07-30, 09-07;
user agent / app version on 09-26, 10-27; watch method on 04-28, 07-11, 10-09; login on 10-25. That's
roughly one breaking-or-maintenance event a month (inference from commit titles).

Design implications (inference):

1. Twitch constants live in one module, and every value has a "last verified" date.
2. A **read-only live probe** (`doctor`) checks hashes, the null catalog, the playlist and the socket.
   It's safe to run in parallel and in CI on a schedule.
3. Every response the miner sees can be recorded (see [04](04-parallel-bug-finding.md)), so a
   shape change shows up as a replayable diff, not as a log line.
